### 17/06/2026 - S1-32: PR #7 review fixes (10-lens self-review)

Addressing a 10-agent CE review pass on PR #7 (no P0/P1 blockers; the action items were P2/P3). Full technical breakdown saved to `docs/pull-requests/PR-7-s1-32-client-detail-17-06-2026.md`. On branch `feat/s1-32-client-detail`.

- **Fixed (reliability)**: the 5s detail poll (`client-detail.tsx`) gained `signal: AbortSignal.timeout(8_000)`, matching the sibling S1-31 list query. The detail view had silently dropped the fail-fast ceiling the list view added one PR earlier, so a black-holed response (LB drain mid-deploy) could hang with no client-side bound.
- **Changed (correctness hardening)**: `_GET_SUMMARY_SQL` is now `SELECT DISTINCT ON (key) ... ORDER BY key, id DESC` instead of the bare `= max(captured_at)`. If two sales-call batches ever share the EXACT same `captured_at`, the old read returned the whole tie-set: duplicate `key`s rendered twice (colliding React keys) and the "which row wins" was non-deterministic across polls. DISTINCT ON guarantees exactly one deterministic row per key. For a contract-compliant single batch (every key already unique) it is a no-op.
- **Discovery**: `client_knowledge` has NO monotonic insertion column - `id` is a random `gen_random_uuid()` and there is no `created_at` (only `captured_at`, the value that ties). So a TRUE "newest-batch-wins on a `captured_at` tie" is impossible from the read side alone; the DISTINCT ON fix makes the read deterministic and duplicate-free but cannot fully isolate two equal-`captured_at` batches that carry disjoint keys. Complete cross-batch isolation needs a monotonic batch key the S1-30 writer owns - folded into the S1-30 writer contract (the read already pins "one transaction, one shared `captured_at`").
- **Fixed**: `inngest.ts` now trims `NEXT_PUBLIC_INNGEST_URL` (`(... ?? '').trim()`) so a whitespace-only value (an operator paste typo) collapses to empty and fails closed (raw run id, no link), instead of emitting a broken relative link like `"   /run?runID=..."` against the dashboard origin.
- **Added (test)**: `test_equal_captured_at_batches_dedupe_to_one_row_per_key` - seeds two batches at an identical `captured_at` with a shared key + disjoint keys, asserts exactly one deterministic row per key across two successive reads. Fails against the old `= max()` query (duplicate `business_type` key), passes with DISTINCT ON.
- **Deferred (logged, owned as a new follow-up ticket)**: a non-latest FAILED `platform_action` can fall off the detail view's recency-ordered top-20 while the list health-badge (latest-started action) shows green - so an unresolved failure can be surfaced nowhere in the UI, in tension with the "partial failures must be visible, never silent" rule. Not reachable at Sprint-1 volumes (clients rarely have 20+ actions) and the list-badge half is pre-existing (S1-31); fix is a separate recency-independent "unresolved failures" query, ticketed before the Sprint-2 fan-outs multiply rows per client. The deferred vitest unit suite (S1-36) remains the home for the front-end pure-helper coverage (`inngestRunUrl` Cloud/unset branches, `humanizeToken`, `startedAgo`, malformed-JSONB degradation).
- **Verified**: `uv run pytest apps/api/tests/test_client_detail.py -q` -> **11 passed** against local pgvector Postgres on :5433 (the new tie test + the existing latest-capture / source-isolation / cross-client cases that exercise the modified query). `ruff check` + `ruff format --check apps/api` clean. `make codegen` unaffected (DISTINCT ON does not change the response shape - no OpenAPI/TS drift).
