### 07/08/2026 - S1-34b review round 4: the flush blocked, so it is gone

Fourth review on `c843371`. All four round-3 P1s confirmed genuinely fixed by the reviewer, who re-verified the core fix independently and **tried and failed to falsify it**. CI 5/5 green (run 31162020018). One blocking item, and it is a deletion.

- **Fixed (P1, blocking - same duplicate-sub-account outcome as round 3, different door)**: bounding the flush to 0.5s stopped it RAISING but not BLOCKING. `before_response` is a SYNC `MiddlewareSync` hook invoked inline (`await transforms.maybe_await(m.before_response())`), so the coroutine never yields, and `sentry_sdk.flush` waits on the **process-wide** transport queue (`BackgroundWorker.flush` -> `_wait_flush` -> `_timed_queue_join` -> `queue.all_tasks_done.wait(...)`), not on this run's event. Under a GHL or R2 outage burst every failing run pays that wait serialised on one transport thread - and the stall does NOT pause httpx timers, so a GHL POST the server ALREADY ACCEPTED can blow its 10s read deadline, raise a transient error and be retried. Nothing is memoised, so the retry re-POSTs the location, and the S1-26d indexing lag means the returning-client check cannot see the orphan. It also stalls `/healthz`, the PandaDoc webhook and the dashboard API on the same dyno.
  **The fix is a deletion**: the flush is gone, and with it the entire `before_response` override and the `_captured` flag that existed only to gate it - plus the two tests that existed only to cover them. On a long-lived Render web service the BackgroundWorker drains continuously, so the flush bought nothing to begin with. One fewer hook that can raise. `sentry_sdk.flush_async` exists if it ever needs revisiting, but "nothing to flush" beats "flush cheaply".
- **Fixed (P2-1, request bodies were reaching Sentry)**: `send_default_pii=False` does NOT gate request bodies on FastAPI - `integrations/fastapi.py` sets `request_info["data"]` unconditionally and `max_request_body_size` defaults to `"medium"` (10 KB). With Inngest failures now captured, that body IS the event payload: for `store_sales_knowledge` a whole `SalesCallSummary` including `notable_quotes[].quote` (verbatim client speech), `.speaker`, `pain_points` and `red_flags`, none of which are denylisted keys. Set `max_request_body_size="never"`. The module docstring asserted the false version of this in TWO places; both corrected.
- **Fixed (P2-2, a replayable credential logged beside the body it authenticates)**: `x-inngest-signature` was in neither `SENSITIVE_HEADERS`, sentry's `DEFAULT_DENYLIST`, nor our `DENYLIST_KEYS`. `_validate_sig` performs no freshness check in 0.5.18 and the body is JCS-canonicalised before the HMAC, so the (signature, body) pair is **replayable against the public `/api/inngest`** by anyone with Sentry read access. Added to `DENYLIST_KEYS` with a test.
- **Fixed (P2-3, the contract guard checked names, not signatures)**: `hasattr` alone would miss an ARITY change within `>=0.5.18,<0.6`, which raises `TypeError` at the SDK's call site - **outside** each hook's own `try/except`, so our guards cannot catch it - and `function.py` converts that into a retriable `CallResult(err)` over an already-successful run. Now compares parameter arity and kinds against the SDK base. Deliberately NOT names: the SDK dispatches positionally, and ours says `output` where the base says `result` because that is what upstream's experimental middleware says.
- **Fixed (P2-4, the secret control had no test)**: `include_local_variables=False` was unasserted, so a silent revert would reopen plaintext secret capture with a fully green suite. Added tests pinning it, `max_request_body_size`, `send_default_pii` and both scrub hooks.
- **Fixed (P2-5, an under-count next to a live secret control)**: the comment claimed SEVEN modules bind `settings = get_settings()` as a frame local. **Fifteen do.** An under-count there reads as a bounded blast radius, which is exactly the wrong impression for a control that exists because the radius is wide.
- **Fixed (operational - the one process whose job is recovery reported nothing)**: `crons/reconcile_pandadoc.main()` never called `init_sentry()`, so a crash in the safety net for missed signings was invisible outside the Render cron log. It now initialises Sentry. Still a no-op until a DSN is set on the cron's own env group.
- **Fixed (docs, and this one mattered most of the small items)**: `test_handler_binds_to_the_sdk_call_shape` claimed to be "strictly stronger than counting positional parameters". **That is false.** `(ctx, step=None)` binds fine but has two positional params, so only the arity test catches it; `(ctx, *, step)` has one positional param, so only the bind test catches it. They are COMPLEMENTARY, and a maintainer trusting that sentence would have deleted the arity test and reopened a real hole. Also corrected: the `sentry.py` claim that `sentry_sdk` "is never imported" (now false - `inngest_sentry.py` imports it at module top and `_inngest.py` imports that unconditionally; only the REGISTRATION is DSN-gated), and a stale "279 passing tests".
- **TRIPWIRE - write this down, because merging alone does not switch observability on**: `render.yaml` declares `SENTRY_DSN` with `sync: false` and it is currently EMPTY, so the middleware is INERT on staging today. That is why this change is materially safe to merge now - the P1 above cannot fire while no DSN is set. It also means **the moment someone pastes the DSN into the Render env group is the moment this module first executes in production**, with no deploy artefact and no CI run behind it. The reviewer raised this in round 3 and it was dropped without comment; recording it here so the next person meets it stated rather than discovered.

### 06/08/2026 - S1-34b review round 3: the observability tool could corrupt what it observes

Third review on `a4210dc`. The signature fix itself was verified correct by the reviewer against `inngest==0.5.18`; **what blocked the merge was the Sentry middleware bolted on beside it**. Every finding below was reproduced in SDK source before being fixed.

- **Fixed (P1, the serious one - telemetry could DUPLICATE the jobs it watches)**: no middleware hook was wrapped. Confirmed in source that this is not merely lost telemetry - `inngest/_internal/function.py:181-186` returns `CallResult(err)` **over an already-successful `call_res`**, and `errors.py:266-269` makes any non-Inngest exception **retriable**. Since no handler uses `ctx.step.run` nothing is memoised, so the retry re-executes every side effect: the GHL location POST, the R2 upload, the `client.created` emit. With the S1-26d indexing lag that can mint a **duplicate sub-account in Bullet's LIVE agency**. Every hook (and `__init__`) is now wrapped in `try/except Exception` and logs via `client.logger.exception`. **The rule is now explicit in the module docstring: no hook may ever raise.**
- **Fixed (P1, unbounded flush on the hot path)**: `sentry_sdk.flush()` with no argument falls back to `shutdown_timeout` (**2.0s**) and BLOCKING-joins the transport on the event loop shared with the PandaDoc webhook and the dashboard API - on every invocation. Now `flush(timeout=0.5)`, and only when something was actually captured, so the success path costs nothing.
- **Fixed (P1, the one that should sting - the middleware had NEVER executed anywhere)**: it is gated on `sentry_dsn`, which is empty in CI, in local dev, and in the 30/07 end-to-end run, and both tests asserted only class membership in `client.middleware`. Not one line of the module had ever run; **staging would have been its first execution** - the same shape as the bug this ticket exists to fix. Added tests that instantiate `SentryMiddleware(fake_client, None)` and drive all three hooks directly, including cases where `sentry_sdk` itself raises, asserting the run result is untouched and the failure is logged.
- **Fixed (P1, live secret exposure - pre-existing, widened by this PR)**: `include_local_variables` defaults to **True** and `init_sentry()` never disabled it; `Settings` has **no** `SecretStr` fields; and **fifteen** modules bind `settings = get_settings()` as a frame local. So the first captured exception in any of those frames would ship `ghl_agency_api_key`, `inngest_signing_key`, `resend_api_key` and `email_token_secret` to Sentry in plaintext. `scrub_event` could not save us - it matches on KEY names, and these arrive nested inside a `settings` repr. Added `include_local_variables=False`. The `SecretStr` refactor is the structural fix and gets its own ticket.
- **Added (L1 - `on_failure` shares the one-arg contract)**: `function.py:153-158` assigns `handler = self._opts.on_failure`, so an `on_failure` declared `(ctx, step)` passed every guard and would fail at RUNTIME - on the branch that only runs when something is already broken. All three guards now iterate every callable the SDK may invoke, not just `_handler`.
- **Added (L2 - `FUNCTIONS` is hand-maintained)**: a decorated-but-never-appended handler is silently never served - the event fires, nothing runs, no error anywhere, the same failure shape as S1-34a. A scan of the worker package now asserts no decorated function is MISSING from the registry. Note this is one-directional and non-recursive, not set-equality - an earlier version of this bullet overclaimed it; tightening the scan is round-4 P2-6, deferred.
- **Added (L3/L4/L5)**: assert the hook names still exist on `MiddlewareSync` (vendoring turns what would have been a loud `ImportError` into a **silent no-op** if 0.5.19+ renames one); tag `ctx.attempt` so one failing job stops raising ~5 indistinguishable events and a recovered blip stops reading as terminal; record vendoring provenance (upstream path, version, dates) so the next SDK bump is diffable.
- **Changed (L6, docs hygiene)**: the 03/08 hardening block was buried inside the `### 29/07` entry below the 30/07 one - promoted to its own dated entry. The "branch stays local and unpushed" note was false as of 06/08 and is corrected in place rather than deleted, since it records a real decision that was later reversed.

Declined, and disclosed here rather than silently: the split was a **Suggestion**, distinct from the four P1 blockers, all of which are fixed as written. **Part 4 of the S1-34b ticket IS "Sentry capture"**, so splitting would close the ticket without meeting its own acceptance criteria; the middleware work turned out to be ~100 lines, mostly tests; and the "ship the P0 today" benefit is largely illusory while staging is deliberately not taking real signings pending the arming decision.

Confirmed in source that `MiddlewareManager.add()` does `middleware(self.client, self._raw_request)` and `from_client` is called per incoming request, so the flag cannot leak between concurrent runs. That guarantee was undocumented and untested, so it now has a test pinning it - if a future SDK shares instances, one failing run would make every later successful run pay the flush, permanently.

### 16/07/2026 - fix(dashboard): same-origin API proxy so the session cookie works cross-host

- **Fixed**: login succeeded at the API but the dashboard bounced straight back to `/login`. Root cause: the API sets an HttpOnly, host-scoped `session` cookie (`SameSite=Lax`, `login.py`), and the dashboard middleware gates every route on `request.cookies.get('session')` - but the dashboard (`bullet-dashboard-staging-web.onrender.com`) and API (`bullet-api-staging.onrender.com`) are DIFFERENT hosts, and `onrender.com` is a public suffix, so a shared parent-domain cookie is impossible and the middleware could never see the cookie. Worked locally only because `localhost:3000` / `:8000` share the host `localhost` (cookies are per-host, not per-port). Surfaced now because the dashboard had never been deployed before 16/07.
- **Changed**: added a Next.js `rewrites()` proxy in `apps/dashboard/next.config.ts` - `/api/backend/:path*` -> `${API_PROXY_TARGET}/:path*`. With `NEXT_PUBLIC_API_URL=/api/backend` (relative) the browser only ever talks to the dashboard's own origin; Next proxies to the API server-side, so the `session` cookie lands on - and is sent back from - the dashboard host, the middleware reads it, and `SameSite=Lax` is fine (now first-party). This also sidesteps CORS entirely for the browser. Local dev is unchanged (both env vars unset -> falls back to direct `localhost:8000`, rewrite is a no-op). Two new dashboard env vars on Render: `NEXT_PUBLIC_API_URL=/api/backend`, `API_PROXY_TARGET=https://bullet-api-staging.onrender.com`.
- **Fixed (follow-on, same PR)**: the dashboard middleware (`middleware.ts`) gated `/api/backend/*` too - its matcher ran on all non-`_next` paths, so it redirected the login POST to `/login` (307) before the rewrite could proxy it, and no cookie was ever set. Excluded `api` from the middleware matcher (`/((?!api|_next/...).*)`) so it gates PAGE routes only; the `/api/backend/*` proxy is authenticated by the backend API itself via the forwarded session cookie.
- **Note**: the long-term production alternative is co-locating dashboard + API under a shared registrable domain (e.g. `*.bulletdigitalmedia.com`) so the cookie can be parent-scoped; the proxy is the correct fix for the onrender.com split-host staging (and works for prod too).
